1Executive overview

Memotron is a governed memory system for AI agents. Text episodes go in; an LLM (or a deterministic rule-based transport) extracts candidate facts; a staged “dream” pipeline forms, dedups, supersedes, rolls up and prunes them into a bitemporal property graph; agents retrieve from that graph inside a token budget.

The differentiator is not the graph. It is the ledger. Every mutation is written to a hash-chained, Merkle-rooted receipt stream that supports byte-exact replay, counterfactual re-evaluation under a different policy, and machine-verifiable erasure certificates. You can prove what the system did, and prove that nothing changed the graph without saying so.

Consumers, in the order you will meet them:

  • Claude Code sessions — this repo dogfoods itself. Four lifecycle hooks in .claude/settings.json call memotron hook …, and .mcp.json registers a stdio MCP server.
  • Hosted MCP agents — a Streamable-HTTP server on port 8000, the only workload Kubernetes actually serves.
  • Python applications — importing the Memotron client directly.
  • Operators — a read-mostly admin console and HTTP API on port 8765.

Five things to understand before touching it

  1. Mixin composition is the house style. Three separate classes are assembled from single-purpose mixin modules rather than written as one file. Read §2.2 once and the shape of two thirds of the codebase stops being surprising.
  2. There are two MCP servers with different tool surfaces and different trust models. Conflating them will waste a day — §2.3.
  3. Nothing is deleted. Supersession, pruning and forgetting all invalidate rather than remove. The single exception is crypto-shred, which destroys a key rather than rows (§5.5).
  4. Two time axes. valid_from/valid_to is when a fact was true in the world; created_at and friends are when we recorded it. Reading the wrong one has already caused a data-loss bug (§6.1).
  5. The library is far ahead of the deployment. Read the next subsection before you believe anything a values file implies.

Gotcha

When you create memotron_db, the collation requirement fails silently if you get it wrong. The terraform marks the database manage = false and says to create it out-of-band as CREATE DATABASE memotron_db LC_COLLATE 'C' LC_CTYPE 'C' ENCODING 'UTF8' TEMPLATE template0; — the same triple docker-compose.local.yml carries — giving as the reason that “the app asserts LC_COLLATE='C' at startup”.

It warns; it does not assert. PostgresStorageBackend.__init__ checks at storage/postgres/__init__.py:150 — if not self._engine.is_byte_ordered(): logger.warning(...) — naming the actual collation and saying “Create the database with LC_COLLATE='C'.” But it is one warning line on an otherwise healthy start, and then the store builds, migrates and serves traffic. Nothing refuses.

It survives because the app does not depend on the database's collation: it writes COLLATE "C" into the queries and the index declarations so ordering is byte ordering “regardless of the database's lc_collate” (storage/postgres/_receipts.py:31-34). What actually breaks is list-ordering parity with the SQLite substrate, not the correctness of stored rows — a divergence that only shows up on the managed instance. Check pg_database.datcollate rather than relying on someone having noticed a warning.

On latest it was done correctly — verified live 2026-09-03: memotron_db reports datcollate=C datctype=C encoding=UTF8, while postgres and cloudsqladmin on the same instance are en_US.UTF8, so the byte-ordered form was used deliberately. Prod and load were not checked, and because the step is manual by design (manage = false) the warning applies to them and to every future environment.

2System architecture

Six layers and two external boundaries. Callers reach one of five entrypoints; every entrypoint funnels into one client facade; the facade drives domain engines that are governed by a policy layer and persisted through a storage contract with two interchangeable implementations.

Component diagram

The mixin-composition idiom

This appears three times independently, and it is the single most important structural fact about the codebase:

  • Memotron — 13 mixins (client/__init__.py:449)
  • DreamEngine — 11 mixins (dreaming/__init__.py:315)
  • Both storage backends — 7 plane mixins each (sqlite/__init__.py:74, postgres/__init__.py:63)

The reason is size: these classes would otherwise be single files of 2,000–10,000 lines. The trick that makes it work without a real inheritance chain is one conditional assignment repeated in every mixin module:

src/memotron/client/_crypto.py:32-40 
if TYPE_CHECKING:
    _Base = ComposedMemotron
else:
    # Plain object at runtime, so the composed class's MRO is unchanged.
    _Base = object


class CryptoGovernanceMixin(_Base):
    """Composed into :class:`Memotron`."""

Design decision

Under TYPE_CHECKING, _Base is a Protocol describing the fully composed class, so mypy sees every sibling method on self and type-checks cross-mixin calls. At runtime it is plain object, so the MRO stays flat and no diamond exists. The cost is that the composed class is the only thing that actually works — instantiating a mixin alone is meaningless.

Two consequences you will hit:

  1. The package __init__.py files are re-export barrels. client/__init__.py re-exports roughly 115 names in an explicit X as X chain. That is not clutter — mypy's strict tier sets no_implicit_reexport, so a name that is not explicitly re-exported stops being importable from the package. Add a public symbol to a mixin and you must add it here too.
  2. The composition is machine-enforced. scripts/verify/mixin_dag.py checks the runtime call graph between mixins is acyclic, except for cycles explicitly declared and justified in its DOMAIN_CYCLES table.

Two MCP servers, two trust models

These are genuinely different products that happen to share a library. Confusing them is the standard newcomer error.

agent_memory_mcp (identity-first)

src/memotron/agent_memory_mcp.py plus the agent_memory/ package.

  • FastMCP instance "memotron-agent-memory", served over stdio.
  • Launched by memotron mcp; registered in .mcp.json. This is what this repo dogfoods — the memory_* tools available in a Claude Code session here are these.
  • Identity is scope. Tools take agent_id; the platform resolves which scopes that agent may touch. A caller cannot address an arbitrary scope.
  • ~30 tools: memory_bootstrap, memory_search, memory_remember, memory_publish, memory_promote, memory_outcome, memory_pin, memory_forget, memory_refresh, memory_evolution, memory_explain, memory_log, project_memory_*, tenant_llm_*.

mcp_server (scoped, hosted)

src/memotron/mcp_server.py, 1,362 lines.

  • FastMCP instance "memotron", served over Streamable-HTTP on port 8000. This is what Kubernetes serves, launched via examples/mcp_server.py — note it is not a console script.
  • Scope is a parameter. Every tool takes scope_kind and scope_id explicitly, so the caller names the scope on each call.
  • 31 tools, a wider surface than the agent server: ingestion, retrieval, dream control (run_due_dreams, run_dream_job, redream_epochs), coherence scanning, and human adjudication queues.

Gotcha

The scoped server's trust model assumes the caller is already authorized to name the scope it passes. Combined with the missing authentication layer described in §8.3, that assumption is not currently established by anything in this repository.

The store boundary rule

One sentence in storage/base.py:70-81 explains the shape of most of the storage code: there are no foreign keys across the store boundary.

The contract splits persistence into two surfaces that may live in different databases: MemoryGraphStorage (the temporal property graph — nodes, relationships, scoped reads) and OperationalStorage (everything about memory — the episode queue, job state, receipts, use/outcome events, policy contracts, tenant config). Because they can be separate engines, referential integrity between an operational row and a graph relationship cannot be enforced by either engine. It is enforced by the write paths instead.

Invariant

The Operational Store is the commit anchor. Memory Graph writes must be idempotent and safe to repeat, because a crash between the two writes is resolved by replaying the graph write, not by rolling back the operational one. SQLite even turns PRAGMA foreign_keys off when constructed in split mode (sqlite/__init__.py:116); intra-database FK enforcement is only enabled when one engine genuinely owns both planes.

The composition of two engines is itself guarded at import time:

Layering and naming conventions

  • _name.py is package-private. Every module with a leading underscore is an implementation detail of its package; the package __init__.py decides what escapes.
  • Barrels are load-bearing, not decorative. mypy's strict tier sets no_implicit_reexport, so a symbol missing from the barrel is not importable from the package. Adding a public name is a two-file edit.
  • _common.py means “shared, and deliberately not a mixin method.” Several packages have one. Helpers live there as module-level functions specifically so they cannot recreate a call cycle between mixins from a new direction.
  • Nothing outside memotron.storage may import sqlite3 or reference engine specifics — stated in storage/__init__.py.

Where to put new code: a new caller-facing method goes in the relevant client/_*.py mixin and the barrel; a new pipeline stage goes in a new dreaming/_*.py mixin added to the DreamEngine base list; a new persisted field goes in models/, then storage/base.py, then both engines; a new threshold goes in config/_policies.py.

Three lifecycles, not one

Asking “what happens on a request?” has three different answers here. Conflating them is the standard newcomer error, because they differ in cost, in whether they touch an LLM, and in whether they can write.

run_job(): the transaction spine

DreamEngine.run_job() is where the ordering guarantees live. Its sequence is deliberate at four separate points:

  1. COHERENCE detours before the receipt run begins. Coherence scans receipt their incidents under their own per-scan run managed inside scan_coherence, so run_job returns early for that kind.
  2. One ReceiptRun wraps the whole job, threaded through every decision point, checkpointed at the end. Empty and aborted runs are intentionally left uncheckpointed, so byte replay of such a run fails closed.
  3. The checkpoint and the last-run marker commit in one transaction — so a crash between them cannot leave a checkpointed run that still looks due.
  4. The health gate raises after the checkpoint.
src/memotron/dreaming/__init__.py:479-499 
            # The run's terminal bracket: the checkpoint and the last-run
            # marker commit together, so a crash between them cannot leave a
            # checkpointed run that still looks due.
            with self._graph.transaction():
                self._checkpoint_receipt_run(receipt_run=receipt_run, job=job)
                self._graph.set_job_last_run(job.name, now)
            # WS-24: a blocking health gate fails the run LOUDLY — but only
            # after the checkpoint, so the ledger that proves what happened is
            # complete and replayable before the exception leaves.  A silent
            # degenerate graph is the outcome this refuses to produce; a
            # half-written receipt chain is not an acceptable price for it.
            blocking = next((report for report in run.health if report.blocked), None)
            if blocking is not None:
                policy = self._effective_health(motive=self._config.resolve_motive(job=job, episode_metadata={}))
                if policy.raise_on_block:
                    raise MemoryHealthGateError(blocking)
        finally:
            # Claims are operational bookkeeping, not memory decisions: release
            # this run's dream-work claims on every exit path
            self._graph.release_dream_claims(receipt_run.run_uuid)

Design decision

“Raise after checkpoint” reads like a bug in review — surely you abort before committing? No: the checkpoint is the evidence, not the outcome. A blocking health trip means the graph is degenerate and the run must fail loudly, but the ledger proving what the run did must be complete and replayable before the exception leaves. A half-written receipt chain is explicitly not an acceptable price for refusing a bad run.

Invariant

An embedding failure is classified before it is handled. A transient outage stops the run at that episode, receipts EMBEDDING_TRANSPORT_UNAVAILABLE, and checkpoints everything already completed — the failing episode is never marked processed, so the next cycle re-forms it in full. A deterministic failure (401/403, malformed request) is a misconfiguration, not an outage, and re-raises uncheckpointed. Embeddings feed dedup, clustering and salience — never truth — so losing them must not destroy extraction work already paid for.

The second entry point is worth knowing early because it is the cheapest debugging tool in the system: regovern_scope() re-runs stage-3 governance over already-stored raw candidates with zero LLM calls. Change a threshold, re-govern, and see what the new policy would have kept — without re-ingesting or paying the gateway again.

6.2 Entity relationships

34 tables in the SQLite schema. Twelve carry the load; the rest are registries and audit sidecars, grouped below rather than drawn.

Gotcha

You cannot filter nodes or relationships by a scope_key column, because there isn't one. Scope is a generated virtual column derived from properties_json on SQLite (gen_scope_key, indexed), and an expression index on Postgres. Likewise episodes is uuid, payload_json, created_at — the entire episode lives in JSON. Writing a naive WHERE scope_key = ? against these tables fails; writing a naive JSON extraction bypasses the index and silently full-scans.

SQLite

sqlite/_migrations.py, 683 lines.

  • No migration runner. One idempotent executescript() of CREATE TABLE IF NOT EXISTS, re-run on every construction, plus five _ensure_* probes that ALTER TABLE ADD COLUMN when a column is missing. Additive-only by construction.
  • Context visibility comes from generated virtual columns (gen_scope_key, gen_status, gen_context_visible) with a composite index over them.
  • JSON columns are TEXT named with a _json suffix.
  • The schema's only CHECK constraint is on entity_canon.status.

Postgres

postgres/_migrations.py, 810 lines.

  • Versioned, append-only MIGRATIONS tuple of 8. Never edit a shipped migration; append a new one.
  • Real jsonb, boolean, bigint types — but timestamps stay ISO-8601 text so they remain byte-comparable with SQLite for hash and receipt equality.
  • Context visibility is a partial expression index rather than generated columns.
  • Postgres-only additions: an incrementally maintained scope state hash (V2), a vector table plus a pure-SQL dw_cosine_similarity that works with no extension, and an opportunistic pgvector upgrade if the extension exists (V3).
  • V5 exists purely to fix two indexes that were silently useless in V1 — one indexed a JSON path that is never populated, and two uniqueness constraints were non-unique where SQLite enforced them. A real parity bug, caught and fixed in-migration.

7.2 Embeddings

The default is LocalEmbeddingTransport: character trigrams plus token unigrams hashed into a 256-dimension vector, L2-normalized, pure standard library, no network. Its identifier is local-trigram-256@v1. The OpenAI-compatible alternative stamps openai-embeddings:{model}@v1.

That identifier is stamped onto every stored vector, and a stored vector only participates in comparison if its stamp matches the currently-active transport.

Gotcha

Changing the embedding transport silently disables rollups for every pre-existing vector. Mismatched vectors are treated as absent, never compared across spaces. That is the correct behaviour — a cosine between two different embedding spaces is meaningless — but it is silent. Existing memories simply stop clustering, with no error and no log line. Re-embedding is the only fix.

8Auth, security, and multi-tenancy

Structured as built, then deployed, then designed-but-absent — because those three are very different here, and the gap is the point.

8.1 Envelope encryption and erasure (built, and good)

crypto.py implements a standard KMS-shaped envelope:

  • Each crypto-shred scope gets a random 256-bit data encryption key (DEK). It is never persisted raw — only wrapped by a key encryption key (KEK) held outside the database, and only the wrapped form is stored, in governance_keys.
  • Content is sealed with AES-256-GCM under a random 96-bit nonce into a self-describing token dwsc1$<nonce>$<ciphertext>. Sealing is non-deterministic, so equality comparison on ciphertext is impossible by design.
  • That would break dedup and truth slots — so fields needing equality also get a keyed commitment (a blind index): dwcm1$<purpose>$<mac>, where the MAC is HMAC-SHA256(DEK, purpose \x1f text).

Design decision

The keyed commitment is why the whole scheme works: truth-key equality survives sealing. Two statements about the same subject and predicate still land in the same slot, and dedup still fires, while the content itself is unreadable without the DEK. Destroy the DEK and both the content and the ability to recompute the commitment vanish together.

8.2 Scopes and authorization (built, and enforced)

MemoryScope(kind, scope_id) is the addressable unit everywhere. MemoryPrincipal carries principal_id, tenant_id, optional agent_id, a default scope, an allow-list of scope keys, and a role (user / operator / admin). Policy resolution composes scope → agent → tenant → control plane into a frozen EffectiveMemoryPolicy that carries a full source_trace plus a contract digest, so any resolved policy can be explained after the fact.

Two independent guards exist:

  1. Platform layer — resolve_policy_for_principal refuses any scope outside the principal's effective allow-list.
  2. Core layer — Memotron(authorized_scope_keys=…) is in-process defence in depth for embedded SDK deployments, enforced by three guard methods at client/__init__.py:644-682.

Invariant

tests/test_scope_guard_completeness.py derives — via ast and inspect, not a hand-maintained list — every public Memotron method taking a scope, and asserts each can transitively reach a guard. It exists because a hand-maintained probe list previously missed four entry points that silently skipped the check. This is the house pattern worth copying: fix the class of bug, not the instance.

8.4 Secrets handling

  • One production secret: the gateway virtual key, LITELLM_API_KEY. Only the variable name ever appears in code, logs, receipts or errors — never a value.
  • Tenant LLM credentials configured through the CLI, the MCP tool, or the admin API are sealed with the same content-plane crypto as memory, never stored in plaintext config.
  • Raw credentials appearing in extracted text are rejected outright during materialization — never quarantined, because a credential has no correct storage location. The rejection is per-candidate and does not abort the run: an earlier version re-raised and killed a 119-episode ingest on the first candidate that looked like an sk- key.
  • redaction.py scrubs PII and bearer tokens before extraction when the governance policy sets high sensitivity.
  • .pre-commit-config.yaml runs detect-secrets against .secrets.baseline.

Tech debt

Only LocalKeyManager exists — a KEK held in memory or in a 0600 file beside the SQLite store. crypto.py:26-27 documents AWS KMS / GCP CKMS / HashiCorp Vault as the intended production swap behind the same KeyManager protocol, but no cloud KMS implementation is present in src/. Combined with the MEMOTRON_ALLOW_EPHEMERAL_KEK escape hatch, key custody is the weakest link in an otherwise careful cryptographic design.

10Concurrency, state, and background work

10.1 Single-writer discipline

Almost every concurrency decision in this codebase follows from one premise: one writer per store. If you understand that, the rest stops looking arbitrary.

The storage contract (storage/base.py, first 121 lines) requires: per-call atomicity; a re-entrant transaction() for bracketing a logical operation; read-your-writes; and single-writer discipline. Downstream consequences:

  • Gateway retries carry no jitter — there is no herd to spread.
  • Graph writes must be idempotent, because the operational store is the commit anchor and recovery replays the graph side.
  • Cross-plane referential integrity is a write-path obligation, not a constraint.

10.2 Claims and leases

Concurrent dream runs are made safe by claiming work before doing it, not by locking the whole store. Three things are claimed, and each is claimed because the operation it guards is not idempotent:

What is claimed, and why
ClaimedGuardsWhy it must be
EpisodesFormationExtraction costs money; two runs would both pay the gateway for the same episode
Scope rollup passConsolidationRollup synthesis creates a summary — running it twice creates two
Run scopePruningTemporary-predecessor restoration is a non-idempotent creation

The primitives differ per engine but the contract does not: SQLite uses BEGIN IMMEDIATE, Postgres uses transaction-scoped advisory locks. Claims are released in run_job's finally, and expire after a staleness window so a SIGKILLed process cannot wedge the queue permanently.

Invariant

Claims and processed-episode markers are operational bookkeeping: deliberately outside the receipt ledger and outside graph_state_hash. If they were inside, two runs partitioning a queue differently would produce different state hashes for identical memory outcomes, and replay would fail on a scheduling detail. Cross-process exactly-once behaviour is pinned on both engines by test_exclusive_write_conformance.py.

Idempotency on the read/event side is separate and explicit: memory_use_events and memory_outcome_events both carry UNIQUE(scope_key, idempotency_key), so a retried tool call cannot double-count utility. memory_outcome additionally requires a caller-supplied idempotency key, a judge identity and a judge version — outcomes are only ever recorded from an observed verdict, never inferred.

10.3 The dream worker

Tech debt

This is the most operationally important fact in the document. worker.py is self-described as a skeleton, prints a warning at every startup, has no fair scheduling and no quotas, and no Helm role exists for it. The compose file omits it deliberately, with a comment saying that is why nothing forms memory in the deployed environment.

Therefore: in every deployed environment today, dream jobs run only when something calls them interactively — an MCP run_due_dreams or memory_refresh, or the admin /api/dream-sequence/run route. An idle deployment forms nothing and reports no error.

What the worker does implement is reasonable: run_cycle() iterates tenants sequentially calling run_due_dreams, containing failure per tenant rather than per cycle, and run_forever() sleeps the interval ±10% jitter. Cadence is not the worker's decision — each DreamJob carries its own cadence_seconds (defaults: formation 60 s, consolidation 300 s, pruning 600 s) and run_due_dreams decides what is due. The worker only supplies a clock.

Its own docstring gates production on Postgres row-lock claims — i.e. on the Operational Store cutover, which is disabled everywhere. So the worker and the Postgres store are one blocked workstream, not two.

The only background loop running anywhere today is local_platform's maintenance thread: every ~15 seconds it builds a fresh platform and runs due dreams, swallowing exceptions into a log call. That is a developer convenience, not a production scheduler.

10.4 Async model

The pipeline is async throughout (pytest runs with asyncio_mode = "auto"), but the concurrency is I/O overlap against the gateway, not parallel graph mutation. Storage calls are synchronous and serialized under the single-writer rule. There is no task pool, no worker fan-out, and no shared mutable state between runs beyond the store itself — which is why claiming, rather than locking, is sufficient.

11Error handling, logging, observability

The honest summary: this system is auditable but not observable. You can prove in forensic detail what it did last week. You cannot tell what it is doing right now.

Measured on this tree: 6 getLogger call sites across 149 modules, 34 print() calls, and zero occurrences of OpenTelemetry, Prometheus, statsd or Datadog. 11.2 What is instrumented

Deep dive — why so many bespoke gates?

Each instrument catches a class the others structurally cannot, and the set was assembled by finding real escapes:

  • pure_move.py proves a refactor commit's bytecode is unchanged — but a symbol moved to a new module has identical bytecode at a different import path.
  • api_surface.py catches that, by runtime-importing and recording the composed surface — but it cannot see a moved method body that gained or lost a storage call.
  • storage_golden.py catches that, by recording a per-test multiset of storage-method call counts.
  • receipt_golden.py is stronger again for receipted writes, pinning the exact ordered receipt stream — the only thing that could certify collapsing ~30 hand-rolled hash/write/emit brackets into one context manager.
  • parity_postgres.py exists because the object-level parity suite does not assert that a scoped read returns the same rows to a caller; it caught a Postgres path omitting a filter and a KeyError from search().

The cultural pattern worth taking away: when a bug escapes, this repo adds the instrument that makes the whole class impossible, rather than a test for the instance.

13Intricacies and gotchas

Ranked by how likely you are to trip over them. Each entry is symptom → cause → file → why the fix is shaped that way. Several look like bugs and are not; two look fine and are not.

13.1 The scope stops forming memory as it learns more

Gotcha

Symptom: memory_publish then memory_refresh forms zero memories. The gateway is billed. No error, no receipt, no log line.

Cause: the formation_episode_selected approval gate was being handed the scope's existing memories as context. A real agent then judged the state of the world described in that context rather than the episode in front of it, and refused — “Reject formation episode: deployment infrastructure lacks required durability guarantees”. Reproduced 5/5 with a single unresolved negative fact injected; three benign facts at the same count were approved, isolating the variable to the content of that argument.

Fix: context_facts=() at dreaming/_formation.py:338-359.

Two things make this the most instructive bug in the codebase. First, the failure scaled with success: incidents, blockers and open requirements are exactly what an engineering scope accumulates, so the more a scope remembered, the less able it became to remember anything new — and it recovered only if someone forgot the offending fact. Second, the fix is deliberately narrow:

Design decision

_consolidation.py:115 still passes graph context to its decision gate, and must keep doing so — reasoning over existing memories is what consolidation is. Equally, graph_context is still computed during formation and still reported as graph_context_count on the decision record: the context is withheld from the prompt, not from the audit trail. Anyone "cleaning up" either asymmetry will reintroduce the bug or destroy the evidence that found it.

13.2 Pruning deletes fresh facts on the very first run

Symptom: 7 of 8 newly-ingested state facts archived immediately. Cause: the staleness helper fell back to valid_from, and the source documents carried historical approval dates. Fix: read transaction time — properties["last_seen_at"] else created_at, never valid_from. Covered in full at §6.1; repeated here only because it is the highest-consequence instance of the two-axis confusion.

13.3 A sort raises TypeError only when one row is missing a bound

Symptom: can't compare offset-naive and offset-aware datetimes, rarely. Cause: three sort comparators fell back to naive datetime.min/.max when a bound was absent, while every stored datetime is timezone-aware. The bug only fires when one row in a result set lacks a bound and another has it. Fix: aware sentinels _AWARE_MIN/_AWARE_MAX at client/_common.py:22-25.

Gotcha

This was found by ruff's DTZ901 rule, not by the test suite — it was invisible to 1,000+ passing tests. Now connect that to §12.3: the lint lane is not in CI. The instrument that caught this class of bug does not currently gate a deploy.

13.4 Rollups silently stop happening after a config change

Symptom: clustering quietly produces nothing; no error. Cause: every stored vector is stamped with its embedding transport's identifier, and a vector whose stamp does not match the active transport is treated as absent rather than compared. Why it is right: a cosine between two different embedding spaces is meaningless, so refusing is correct. Why it hurts: it is completely silent. See §7.2.

13.5 Editing graph.py or receipts.py changes nothing

Both are compatibility shims. The real implementations are storage/sqlite/ and storage/receipts.py. See the callout in §3.3.

13.9 Receipt payloads are a compatibility surface

canonicalize_payload hard-errors on naive datetimes and on NaN/Inf, and renders floats as repr(round(x, 10)). Adding a float to a receipt payload is therefore a compatibility event, not a cosmetic change: it alters bytes that are hashed, chained and compared against a committed golden file.

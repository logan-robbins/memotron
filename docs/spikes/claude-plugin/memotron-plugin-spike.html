Memotron as a Claude Code plugin

Every piece this spike asked about — an MCP connector, skills, and a hook for “dreaming” — already exists in Memotron today. It's just distributed by hand, one repository at a time. Packaging it as an installable Claude Code plugin is mechanical restructuring, not new invention.

Context

Memotron is a typed, temporal, governed memory graph for coding agents — identity, preference, requirement, directive, state, decision, incident, and theme facts, formed and pruned by an offline Dream Engine. It already talks to Claude Code today, but the integration is hand-installed per repository: uv tool install jedai-memotron, then memotron init, which writes a project .mcp.json, four .claude/settings.json hooks, an always-loaded rule file, and a /memotron-memory skill observed — see src/memotron/adoption.py.

The question behind this spike was whether that bundle could instead be one Claude Code plugin: a single install unit combining the MCP connector, the skills, and — the part that sounded like it might need inventing — a hook that drives “dreaming.” It turns out dreaming is not a metaphor to build toward; it's already the name of the thing. src/memotron/dreaming.py implements a DreamEngine running Formation → Consolidation → Pruning (and an opt-in Coherence pass) jobs, and it is already wired to fire from Claude Code's own compaction lifecycle observed.

Today vs. plugin

The four moving parts don't change. What changes is how they're delivered.

Today — per repository

  • uv tool install jedai-memotron, once per machine
  • cd repo && memotron init, once per repository
  • Writes land into the repo: .mcp.json, .claude/settings.json, .claude/rules/, .claude/skills/
  • Restart Claude Code, approve the MCP server, per repository
  • Updating the integration means re-running memotron init everywhere

Proposed — one plugin

  • /plugin marketplace add jedai/memotron-plugins, once per machine
  • /plugin install memotron-memory@jedai, once per machine
  • Nothing is written into the working repo's own tree
  • MCP server, hooks, and skills auto-attach to every session, in every repo
  • Updating the integration is /plugin update memotron-memory

The dreaming hook

The one open design question going in was: what fires dreaming? The official Claude Code hooks reference settles it directly:

“No idle detection or periodic triggering: Hook events fire only in response to explicit user actions or Claude tool calls, never on a timer or idle state.” code.claude.com/docs/en/hooks — observed, fetched directly

There is no cron-like hook to build toward, so the right design isn't a new mechanism — it's the one Memotron already uses. PreCompact and PostCompact each call memotron hook <event>, which runs platform.memory_refresh(include_project=true) observed, and that in turn executes any due Formation/Consolidation/Pruning/Coherence jobs. Dreaming rides Claude Code's own compaction and session boundaries instead of a background schedule — which also matches the project's own “no background daemon, no fixed port” design goal.

stretch / unconfirmed Monitors as a session-lifetime nudge

Plugins can declare experimental monitors/monitors.json — a persistent shell command whose stdout lines surface as notifications for the life of a session. A polling script could emit “dream cycle due” during a long-lived session. This is not background/cron — it only runs while a session is open — and its config shape wasn't verified against a working example in this pass. Worth a follow-up spike, not part of the recommended design.

Risks & open questions

confirmed risk Distribution bootstrap

A plugin can't assume uv tool install jedai-memotron already happened. The scaffold's bin/memotron-run shim falls back to uv tool run --from jedai-memotron memotron …, which downloads and runs the package on first use with no separate install step — if the package resolves from wherever uv looks. It did not, in this environment:

bash bin/memotron-run --help × No solution found when resolving tool dependencies: ╰─▶ Because jedai-memotron was not found in the package registry ...

jedai-memotron isn't on a registry uv can reach from this machine. Inside this repo's own checkout, uv run memotron --help works fine — but that only helps someone developing Memotron itself, not a consumer repository installing the plugin. Fix before shipping: publish jedai-memotron to an internal index uv is configured to check, or ship a vendored/pre-built binary in bin/ instead of relying on first-run resolution.

confirmed by docs No idle/timer hooks

Already covered above — restated here because it constrains the design, not just informs it. Any future “dream more proactively” feature has to ride an existing event (tool call, compaction, session boundary), not a clock.

scope Spike, not production packaging

This scaffold hasn't been round-tripped through a real /plugin marketplace add + /plugin install + /reload-plugins flow — only the CLI's non-interactive validate and details commands, deliberately, to avoid mutating this machine's global plugin registry. One marketplace with one plugin is the minimum shape for local testing; shipping this org-wide would more likely mean a shared internal marketplace repo alongside other jedai plugins.

Recommended next steps

  1. Resolve the bootstrap risk first — it blocks everything downstream. Publish jedai-memotron somewhere uv tool run can reach, or replace the shim with a vendored binary.
  2. Run the real interactive flow once resolved: /plugin marketplace add → /plugin install → /reload-plugins → confirm memotron_agent_memory tools actually answer calls, not just that the server is declared.
  3. Decide whether the always-loaded rule file is worth replicating in plugin form, or whether SessionStart's own injected context genuinely replaces it — test with a multi-session transcript before deciding.
  4. Pick a home for the real marketplace repo (a new jedai/claude-plugins repo, most likely) rather than nesting it under this spike's docs/ folder long-term.
  5. If proactive (non-hook-driven) dreaming is ever wanted, prototype the experimental Monitors mechanism as its own follow-up spike — don't fold it into this one.
